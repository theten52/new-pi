# 聊天室功能设计文档

> 需求澄清后定稿（2026-09）。本文档记录多模型协作「聊天室」的目标需求，
> 供实现时逐条对照。所有关键决策均已确认闭环。

## 概述

设计一个多人协作聊天室，允许多个 AI 模型在一个房间里协作完成任务。每个模型有
预设的角色身份，可以讨论、执行和 Review。

**与现有对话（Session）完全独立**：聊天室是多模型协作的独立功能，与单模型
Session 互不干扰。但聊天室绑定一个本地项目文件夹，模型可基于该项目的文件思考、
调研和改代码。

## 核心概念

```
聊天室 (ChatRoom)
  ├── 绑定项目文件夹 (projectPath)      ← 工具操作的作用域
  ├── 角色配置 (Role + Provider + Model) ← 复用 providers.json
  ├── 房间全局阶段 (currentPhase)        ← discussion / voting / execution / review / completed
  └── 执行轮次 (reviewRoundCount)  ← 1=初始，2/3=review 后修改，上限 3
```

## 已确认的关键决策（✅）

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 模型引用粒度 | **Provider + Model 组合**（角色存 `providerProfileID` + `modelID`） |
| 2 | Provider / 凭据 | **复用现有 `providers.json` + keychain**，角色从已配置 provider 选模型 |
| 3 | 执行阶段语义 | **Agent 用工具实际改代码**（非只产出文本），走简化审批 |
| 4 | 共识检测 | **用户驱动**：手动结束讨论 + 直接指定方案 或 发起投票，不做关键词/自动 LLM 检测 |
| 5 | 发言推进 | **手动推进**（用户触发下一个发言者） |
| 6 | 阶段流转 | **房间全局状态机**；Review 发现问题可回执行重走流程 |
| 7 | 上下文管理 | 第一版**不做自动 compaction**；按「最小 context window」设预算提示 |
| 8 | 轮数控制 | **总 3 轮**：第 1 轮初始实现 + 第 2/3 轮 review 后修改；第 3 轮 review 未过则暂停，用户手动解锁/加轮 |
| 9 | 与现有系统关系 | **与 Session 完全独立**；聊天室绑定独立本地项目文件夹 |
| 10 | 工具权限 | **能用工具**（调研 + 执行），**简化审批**：读文件自动通过，写文件需用户审批 |
| 11 | 投票 | **讨论 → 投票 → 执行**；候选方案支持 JSON 格式输出，回退到字符串解析 |
| 12 | 恢复粒度 | **完整恢复（断点续跑）**：恢复阶段、轮次、发言者索引 |
| 13 | 分支（并行方案） | **砍掉**，第一版不做 |
| 14 | 工具结果回传 | **Agentic loop**：工具结果回传给模型继续，支持多轮工具调用（最多10轮） |
| 15 | 工具分阶段 | **所有阶段都可以使用所有工具**（不区分讨论/执行） |

## 用户场景

### 典型流程

```
用户: "帮我重构这段代码"

[讨论阶段]
架构师: 建议用简单工厂模式
程序员: 同意，这样更简单
用户: 我也同意
→ 用户点「结束讨论」

[投票阶段]（若有多个候选方案）
方案A: 简单工厂    ← 用户投票
方案B: 策略模式
→ 用户确认方案A

[执行阶段]
程序员: 正在实现...（用工具改代码，走审批）
架构师: 建议加个缓存
程序员: 好的

[Review 阶段]
测试员: 发现一个边界情况没处理
程序员: 已修复
测试员: LGTM ✅
→ 完成
```

## 功能清单

### 1. 聊天室管理

| 功能 | 说明 |
|------|------|
| 创建聊天室 | 输入名称、描述、绑定项目文件夹、选择角色 |
| 删除聊天室 | 需要确认 |
| 编辑聊天室 | 修改名称、描述、角色配置（对话开始前） |
| 列表展示 | 显示所有聊天室 |

### 2. 角色配置

#### 预设角色

| 角色 | 职责 | 推荐模型 |
|------|------|----------|
| 架构师 | 系统设计、方案决策 | Claude Opus |
| 程序员 | 代码实现 | GPT-4o / Claude Sonnet |
| 测试员 | 代码审查、找 bug | Gemini Pro |
| 产品经理 | 需求分析、用户体验 | Claude Sonnet |

#### 角色属性

```swift
struct ChatRoomRole: Codable, Identifiable {
    var id: String              // 角色 ID
    var name: String            // 角色名称（如"架构师"）
    var description: String     // 角色职责描述
    var systemPrompt: String    // 系统提示词
    var icon: String            // SF Symbols 图标
    var providerProfileID: String?  // 关联的 provider（复用 providers.json）
    var modelID: String?        // 关联的模型 ID
}
```

#### 模型选择

- 每个角色可独立选「provider + model」（复用已配置的 providers.json）
- 对话开始前指定；对话过程中不可更改
- 角色的 provider / model 为 nil 时，该角色暂不参与发言

### 3. 发言模式

- **手动推进（默认）**：用户点击触发下一个发言者（按角色顺序轮转）
- **用户指定**：用户 @某个角色，指定下一个发言者
- **用户插话**：用户随时发消息，所有模型可见

### 4. 用户介入方式

| 方式 | 说明 |
|------|------|
| 插话 | 用户随时发消息，所有模型可见 |
| 指定发言人 | 用户 @某角色 |
| 投票 | 讨论结束、进入执行前，用户对候选方案投票 |
| 终止 | 用户手动结束讨论 / 停止整个流程 |

### 5. 讨论阶段

1. 用户提出问题
2. 用户手动触发各角色轮流发言
3. 用户可插话、指定发言人
4. 用户点「结束讨论」→ 直接指定方案，或进入投票

**结束条件**：仅由用户手动结束（无自动共识检测）。讨论产出为候选方案（自然语言
归纳，可由模型在讨论末尾结构化输出，或用户手动归纳）。

### 6. 投票阶段（讨论 → 执行之间）

- 讨论结束时，模型**结构化输出候选方案**（方案标题 + 简要描述）
- 若存在多个候选方案，进入投票
- 用户投票选定方案；各角色可表态作参考
- 用户最终确认后进入执行阶段
- 若用户直接指定方案，可跳过投票

### 7. 执行阶段

1. 被指定的角色（通常是程序员）**用工具实际改代码**
2. 工具调用走统一对话式审批策略
3. 其他角色可提建议
4. 执行完成 → 进入 Review 阶段

### 8. Review 阶段

1. 测试员（或其他角色）审查代码改动
2. 发现问题 → **回到执行阶段**，`reviewRoundCount += 1`
3. 审查通过 → 完成

**轮数定义**：
- 第 1 轮：初始实现（方案落地，首次写代码）
- 第 2 轮：第 1 次 review 发现问题 → 修改
- 第 3 轮：第 2 次 review 发现问题 → 修改（最后一轮）
- 第 3 轮 review 仍未通过 → 流程暂停，用户手动解锁或追加轮数

### 9. 展示方式

分组展示（按房间全局阶段 + 历史消息分组）：

```
┌─────────────────────────────────────────┐
│  聊天室: 重构认证模块                      │
├─────────────────────────────────────────┤
│  💬 讨论                                 │
│  │ 架构师: 建议用简单工厂模式            │
│  │ 程序员: 同意，这样更简单              │
│  │ 用户: 我也同意                        │
│  🗳️ 投票                                 │
│  │ 方案A: 简单工厂  ← 已选               │
│  🔧 执行                                 │
│  │ 程序员: 正在实现...                   │
│  ✅ Review                               │
│  │ 测试员: LGTM ✅                       │
│                                          │
│  [输入框] [推进下一发言] [@指定] [投票] [停止]│
└─────────────────────────────────────────┘
```

### 10. 上下文管理

- 共享上下文：所有模型看到完整对话历史 + 各自 systemPrompt
- 第一版**不做自动摘要/compaction**
- 预算提示：共享上下文上限 = 所有角色中最小的 context window；
  累计达到其 80% 时 UI 提示「建议结束当前讨论」
- 后续需要时复用现有 compaction 逻辑

### 11. 工具与审批

- 角色具备工具能力（讨论阶段调研 + 执行阶段改代码）
- **简化审批**：读文件、列出目录、搜索文件自动通过；写文件需用户审批
- **Agentic loop**：工具结果回传给模型继续，支持多轮工具调用（最多10轮）
- **所有阶段都可以使用所有工具**（不区分讨论/执行）

### 12. 存储

聊天室与 Session 完全独立，绑定本地项目文件夹：

```
~/.new-pi/agent/chatrooms/
  └── {chatroom-id}/
        ├── chatroom.json    # 聊天室配置（含绑定项目路径、角色、当前阶段、轮数）
        └── messages.jsonl   # 对话记录
```

> 绑定项目文件夹用于工具操作的作用域（读/改该项目的文件），但聊天室数据本身
> 存储在 agent 目录，与项目文件夹解耦。

## 数据结构

### ChatRoom

```swift
struct ChatRoom: Codable, Identifiable {
    var id: String
    var name: String
    var description: String
    var roles: [ChatRoomRole]
    var projectPath: String       // 绑定的本地项目文件夹
    var currentPhase: Phase       // 房间全局阶段
    var reviewRoundCount: Int     // 当前执行轮次（1=初始实现，2/3=review 后修改，上限 3）
    var selectedOptionID: String? // 投票选定的方案
    var votes: [Vote]             // 投票记录
    var currentSpeakerIndex: Int  // 当前发言者索引（断点续跑用）
    var createdAt: Date
    var updatedAt: Date
}
```

### ChatRoomMessage

```swift
struct ChatRoomMessage: Codable, Identifiable {
    var id: String
    var chatroomID: String
    var roleID: String          // 角色 ID（或 "user"）
    var content: String
    var phase: Phase            // 该消息产生时所处阶段
    var timestamp: Date
}

enum Phase: String, Codable {
    case discussion
    case voting
    case execution
    case review
    case completed
}
```

### 阶段状态机（房间全局状态）

```
discussion ──(用户结束，多方案)──▶ voting ──(用户确认)──▶ execution
     │                              │
     │                              └──(用户直接指定方案，跳过投票)
     └──────────────────────────────▶ execution

execution ──(执行完成)──▶ review
review ──(通过)──▶ completed
review ──(发现问题，轮次 < 3)──▶ execution（进入下一轮修改）
review ──(发现问题，轮次 = 3)──▶ 暂停，等用户解锁/加轮
任意阶段 ──(用户停止)──▶ 结束
```
