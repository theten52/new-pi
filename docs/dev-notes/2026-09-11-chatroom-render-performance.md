# 聊天室性能基线与列表通知隔离

基线：`e7b1daf`，分支：`codex/chatroom-render-performance`。

## 范围

本轮只缩小通知范围，不改消息模型、流式合并、Markdown、滚动、目录规则、四行输入框。
生产代码只修改 `NewPiChatRoomStore.swift`；新增基准脚本和扩充 App 层检查。

原链路：runtime 任意发布 → FlowController.objectWillChange → Store.objectWillChange → 根视图失效。
新链路：正文/Thinking/用量仍通知详情，但不传播到 Store。
Store 继续接收聊天室元数据、忙碌状态翻转和目录健康变化。

## 实现要点

- `busyChanges` 用 CombineLatest3 组合任务活跃、runtime.isRunning、是否有待审批，再对整体布尔值去重。
- 不能在 `objectWillChange` 回调里重新读取 `isBusy` 判断新状态，因为 @Published 在 willSet 时发射，属性此时仍是旧值。
- 订阅忙碌和目录 publisher 时忽略初始发射，避免惰性创建控制器时无意义地通知根视图。
- 删除、编辑等最终守卫仍直接读取实时 `isBusy`，不依赖延迟缓存或 UI 是否刷新。
- 元数据保留原有同步；阶段/名称/时间变化继续同步到列表。
- 目录健康不变时不重复发布；目录失效/恢复继续更新侧边栏警告。
- 存储可注入临时 ChatRoomStore，测试不会对用户已有聊天室执行保存/删除。

## 原生基线

脚本：`bash scripts/validation/check-chatroom-performance.sh`。
对照：设置 `NEWPI_CONTROLLER_REVISION=e7b1daf` 只替换编译的控制器源码，不更改工作区。

真实控制器、适配器、条目模型及共用 signature 函数；Swift 探针使用 `-O`，Core 使用 Debug 构建。
每个场景预热一次，再连续合成 100 次正文更新。
计时分为适配和签名生成/比较；**不包括完整 Coordinator diff、JSON 编码、SwiftUI 布局或原生→JS 通信**。
消息数包括当前流式消息，工具场景每条历史有 Thinking、正文及工具结果。

## WKWebView 基线

`NEWPI_TRANSCRIPT_PERFORMANCE=1 bash scripts/validation/check-transcript-dom.sh`。
独立 WKWebView，加载真实 JS/CSS。每场景一次首次 apply，后续 30 次更新只传活跃消息，每次之间等待两个 RAF。
场景与原生侧体量相近，但没有适配器插入的阶段行，不用于逐项端到端对齐。

| 场景 | DOM 行 | 首次同步 apply（ms） | 增量 apply P50/P95（ms） |
|---|---|---|---|
| 短对话 | 21 | 5 | 1 / 1 |
| 长对话 | 501 | 470 | 3 / 5 |
| 多工具历史 | 801 | 213 | 3 / 4 |

该计时含 JSON 序列化、DOM 修改及同步强制布局，不含跨进程排队、异步绘制、GPU 提交和屏幕呈现。
不是 App 的 FPS 或用户可感知延迟。JS 本轮未修改，这里只有基线，不声称前后 JS 性能提升。
首次载入明显比单次增量更新贵，后续应优先用真实长会话测冷加载，而不是直接重写所有更新链路。

## 回归覆盖

`scripts/validation/check-chatroom-controller.sh` 现在使用临时存储，检查：

- 正文、Thinking 身份、用量等仍通知详情，不通知根列表。
- 前台/后台控制器的正文都隔离；忙碌边界同步通知。
- 阶段、名称、更新时间、目录失效/恢复仍同步列表。
- 任务刚启动、取消待收尾、待审批时禁止删除。
- 多个忙碌原因重叠期间不误发空闲通知；最后一个原因解除才发布空闲。
- 相同忙碌状态、相同目录健康不重复发布。
- 删除控制器后解除其订阅，外部残留引用不再影响列表。

原来的适配器与实际 WKWebView DOM 正确性脚本仍保留。

执行结果：Debug / Release 构建通过；Swift Package 282 tests / 79 suites 通过；扩充后的控制器守卫、适配器/Session 兼容及真实 WKWebView DOM 检查均通过。
构建仅有 AppIntents 未依赖时的 metadata extraction 提示。
