## 一、需求定稿（与用户逐条对齐）

| # | 需求 | 强度 | 最终承载机制 |
|---|---|---|---|
| R1 | 切换会话零重载、直接展示最终结果 | 强（切换频繁） | 产物重放 + 保活 LRU |
| R2 | 快速定位任意消息（rail + 原位恢复） | **强** | 高度表算术定位 + 锚点恢复 |
| R3 | 渲染观感逐像素一致 | 强 | 重放同一引擎产物（结构性保证） |
| R4 | 流式体验不变（块级增量 + ✦ 光标） | 强 | 未动 |
| R5 | 揭示后滚动条高度稳定 | 中 | 手动窗口化 + 全量预热 |
| R6 | 不急切全量挂载 WebView（防白屏） | 硬约束 | 窗口化只挂可见区 |
| — | 暗色模式 | 暂缓 | — |
| 规模 | 几十条消息/会话 | 关键前提 | 决定预热/窗口化可行 |

**用户关键直觉**（后来成为方案核心）："动静分离——历史消息直接展示结果，不需要渲染；渲染后的结果文件/数据单独存储。"

## 二、方案选型结论

**产物重放（WebView 静态 HTML 回放）胜过全原生渲染（方向 B）**，决定性因素是 R3：
重放是同一引擎同一份输出的结构性逐像素一致；原生渲染只能无限逼近 markdown-it + hljs。
全原生唯一不可替代的优势是跨消息文本选择/Cmd+F——判为可接受取舍。
方向 B 保留为长期选项，触发条件：① 会话规模涨到几百条以上；② 跨消息选择升级为强需求。

**取舍问答中用户不知道的部分**（"哪些因素会改变渲染结果"）由机制兜底：
引擎指纹 = MarkdownRenderer 目录资源哈希，任何渲染器/样式变更自动整体失效重捕获。

## 三、最终实现架构

```
消息 flush 完成 → JS 回传最终 innerHTML（剥光标）→ 缓存 {内容SHA256, 宽度桶, 引擎指纹} → {html, height}
                                                            ↓
会话打开/切换 → 命中缓存的行：replayDocumentHTML 预填产物（不解析、无光标、无修复）
                                                            ↓
TranscriptHeightMap（唯一几何真相）：md 行读缓存 / 文本行纯函数+实测持久化 / 工具行固定高
                                                            ↓
手动窗口化：可见区 ±1 屏真实行，其余 Color.clear 精确占位（LazyVStack 退役）
                                                            ↓
rail = 前缀和 + scrollTo(point:) ｜ 原位恢复 = 锚点行 + 行内偏移（持久化）
```

## 四、Bug 与修复全记录

### B1. 重放页收到流式更新内容重复（防御性修复，`3aa2e33`）
- **机制**：重放页 `renderedBlocks=[]` 但 DOM 有内容；意外流式更新会 append 到已有内容后。
- **修**：`renderStreaming` 开头检测非增量状态先清空。可达性极低，按项目"宁可防御"惯例守住。

### B2. 长会话滚动条"越滚越短"（`0b95bb0`）
- **现象**：加载揭示后滚动条长，滚动时变短。
- **根因**：高度缓存只覆盖"渲染过的行 + 尾部 8 条预热"；中段行未实例化时按估算参与布局。
- **修**：预热全量化（所有 cache-miss 行，上限 120），探针同时捕获产物（html+height）。

### B3. rail 三轮不收敛 → 两次重构（`0b95bb0` → `6acb1c2`）
- **第一次重构（高度表算术定位）**：点击 = 前缀和 + scrollTo(point:)。结果"有准的有不准的"。
- **致命盲区**：高度表算得准，但 **LazyVStack 对未实例化行用自己的内部估算参与布局**——
  布局根本不用这张表。"算好 y 再跳"与 LazyVStack 在原理上不相容。
- **第二次重构（手动窗口化）**：布局几何整体收归高度表，可见区外精确占位，
  不存在任何估算。rail 与滚动条稳定同源根治。即文档 §六 原则 P1。

### B4. 揭示后白屏、滚动才恢复（`7794a21`）
- **现象**：某些会话揭示后内容区全白（rail/composer 正常），滚动一下恢复。
- **根因**：`visibleRange` 是命令式 @State，靠事件链更新（onAppear→rebuild→pin→offset 变化→重算），
  时序错位即窗口过期——当前视口内没有任何行被实例化。
- **修**：窗口改为 body 内派生值（scrollOffset × 视口 × prefixSums），事件链维度整个删除。
  即原则 P2。顺带：门控超时 1.2s→0.6s（占位精确后，结构先行内容陆续填入）；
  resize 防抖 500ms 重预热补齐新宽度桶。

### B5. 原位恢复被 composer 钉底覆盖（`577183e`）
- **现象**：重开会话永远停在底部。
- **根因**：onAppear 恢复 scrollTo 生效后，composer 实测高度回报触发 onChange →
  `schedulePinScrollToBottom`（isNearBottom 初始 true）→ 拽回底部。
- **修**：恢复过保存位置的会话禁止 composer 高度变化触发钉底。

### B6. 两个长会话跨重启恢复失败（`9020f08`）
- **现象**：99 条消息会话、单条 200 行消息会话恢复不到离开位置；其他会话正常。
- **根因**：这两个会话 cache-miss 最多。恢复时大量行还是 44pt 估算，内容总高远小于
  真实值 → 保存的绝对 offset 超出当时内容长度 → 被钳制到底部。
- **修**：**锚点制**——存「视口顶部消息行 ID + 行内偏移」，恢复按锚点重算；
  接入有界跟进校正（预热补齐几何后锚回同一条消息）。绝对 offset 降级为兜底。
  即原则 P3。旧格式存档自动迁移（首次打开后滚动一下即写新格式）。

### 辅助：诊断能力建设（`de40808`）
- 恢复落地验证（8×120ms 有界重试）+ 恢复决策/钉底全程 NewPiLogger 日志（View Logs 可见）。
- 教训贯彻：**视觉/时序问题先埋点拿证据，不凭推理连改**（对照 rail-jump-fix-status.md 的同源教训）。

## 六、沉淀的设计原则（后续改动必须遵守）

- **P1**：滚动几何只允许一个真相源。布局用的行高与定位用的行高必须同源；
  任何依赖"容器对未实例化行的估算"的定位方案在原理上不可能精确。
- **P2**：能从状态派生的值，绝不用事件链维护。（visibleRange 白屏 vs 派生值）
- **P3**：跨会话/跨启动的位置用锚点（消息 ID + 行内偏移），不用绝对 offset——几何会变。
- **P4**：渲染产物是数据。内容哈希 + 宽度桶 + 引擎指纹三元组寻址，"重放"代替"重算"。
- **P5**：跟进校正只追「数据稳定」，不追「异步实测」，且必须有界（deadline + 用户接管即放弃）。

## 七、待议 / 后续项

1. **门控去留**：窗口化 + 重放后实测若 600ms 都嫌多，可完全删除门控（即刻揭示，内容渐进填入）。
2. **跨消息文本选择 / Cmd+F**：WebView 每消息一个选择域的固有短板；升级为强需求时重启方向 B 评估。
3. **rail 微残差**：You 气泡等文本行的纯函数估算可能有 ±2–4pt 误差（实测回报+持久化已大部分吸收）；
   若实测仍可见偏差，校准 `TranscriptHeightMap` 布局常量即可，勿动机制。
4. **方向 B（全原生）触发条件**：会话规模几百条+ / 跨消息选择强需求。
5. 分支可合并：日常用一两天无反复即可合入 main。
